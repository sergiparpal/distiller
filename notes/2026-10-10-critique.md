# Revisión adversarial: SPEC Distiller, Slice 1

## Bloqueantes

**1. La configuración del floor no tiene formato ni ubicación definidos.**
Frase: «the repository's floor configuration, if it has one» y «`floor` for a floor configuration that cannot be read or has an invalid pattern».
Problema: la spec nunca dice dónde vive (¿qué archivo, en el checkout en H? ¿un flag?), ni su sintaxis (¿TOML, lista de patrones?). Los ejemplos de floor («Given a floor configuration that adds `data/**`») y toda la vía de rechazo `floor` dependen de un input que cada implementación tiene que inventarse; ni siquiera los tests de aceptación se pueden escribir sin inventar el fixture. Si el formato vive en §9.3 del doc C6, esta spec no lo dice.
Arreglo: fijar ruta exacta y sintaxis (p. ej. un archivo de texto con un patrón por línea), y si remite a C6 §9.3, decirlo explícitamente.

**2. El comando del diff no está fijado y el comportamiento por defecto de git contradice la regla de renombres.**
Frases: «the diff is `merge-base..H`, the pull request's own change», «A renamed path counts under both of its names, a deleted one under its old name», con el ejemplo «renames `src/shop/tax.py` to `src/shop/taxes.py` … through the old path».
Problema: `git diff` trae detección de renombres activada por defecto (desde 2.9); con `--name-only` un rename aparece como una sola entrada con el nombre **nuevo**. La regla y el ejemplo exigen los dos nombres. La implementación "natural" de la frase citada produce otro conjunto de paths y, en renombres reales (frecuentes), selecciona de menos: el path viejo ya no dispara `covers` ni `own file`. Además el edge case de las comillas de git («never listed as having no column because of how `git` quotes it») depende del flag exacto, que no se nombra.
Arreglo: especificar el comando, p. ej. `git diff --name-only --no-renames -z <merge-base> <H>`: `--no-renames` materializa el rename como baja+alta (ambos nombres) y `-z` elimina el quoting de rutas con espacios o no-ASCII.

## Mayores

**3. Precedencia entre causas de rechazo sin definir.**
Frase: «A run is rejected for one of these reasons, each recorded with its input.»
Problema: un run real puede fallar por varias a la vez (H que no nombra commit y JUnit ausente; M no ancestro y JUnit con entidad; `no-shared-lines` y `unsafe-xml`). Sin orden de comprobación, dos implementaciones registran pares (reason, input) distintos; y como la deduplicación de rechazos es por (key, reason, input), el mismo run deja uno o dos registros según la implementación.
Arreglo: declarar el orden normativo (p. ej. el orden en que se enumeran los inputs de `unusable-input`, luego ancestro de M, luego XML seguro, luego `no-shared-lines`).

**4. `missing-history` y `coverage-not-ancestor` son indistinguibles con git.**
Frase: «`missing-history` … when the checkout lacks the history to prove that M is the merge-base or one of its ancestors, as in a shallow clone».
Problema: `git merge-base --is-ancestor` sale 1 tanto si M no es ancestro como si la historia que lo probaría falta en un clon shallow (el caso normal en CI con `fetch-depth` limitado). El criterio de elección entre las dos causas no existe.
Arreglo: procedimiento explícito: si `--is-ancestor` no confirma y el repo es shallow (`git rev-parse --is-shallow-repository`) o git da error, `missing-history`; si no, `coverage-not-ancestor`.

**5. La forma del registro queda ambigua justo en los casos que la propia spec anticipa.**
Frases: «`failed_left_out` … each an object with `pair`, `node_id` and `row`», «An unmeasured test has no node id», «When two node ids have the same pair, the tests with that pair count as unmeasured».
Problema: (a) Un test fallido **no medido** que queda fuera (nuevo, renombrado, `record_xml_attribute`): ¿qué se escribe en `node_id` y `row` — `null`, `""`, `[]`, clave omitida? El registro es el output central y el ejemplo [core] solo cubre el caso medido. (b) Cuando dos testcases del JUnit comparten par (colisión `v1.2`/`v1/2`), ¿`tests` cuenta uno o dos? La spec dice «is one failed test» para failure+error del mismo test pero «the tests» (plural) para la colisión, y el JUnit no permite distinguir ambos casos. ¿`failed_left_out` y `not_reproduced` deduplican por par? ¿Los node ids duplicados de los contextos cuentan en `tests_with_row` / `tests_with_row_not_in_run`?
Arreglo: fijar todo: `node_id`/`row` a `null`/`[]` cuando no aplican; conteo de tests como testcases tras fusionar repeticiones del mismo par; deduplicación por par en las listas.

**6. El mapeo de rutas de cobertura es un ejemplo, no una regla.**
Frase: «coverage recorded absolute paths under another checkout root (`/runner/work/shop/src/shop/tax.py`) -> matched to `src/shop/tax.py`; a recorded file outside the repository is not a column».
Problema: no se dice cómo se mapea (¿sufijo? ¿prefijo configurado?), qué pasa si el repo usa `relative_files = true`, si el mapeo distingue mayúsculas (macOS), ni qué pasa cuando un sufijo casa con varios archivos del repo. Decidir «fuera del repositorio» presupone exactamente la regla que falta.
Arreglo: definir el algoritmo (p. ej. ruta absoluta → recortar por el sufijo más largo que coincida exacta y sensiblemente a mayúsculas con un path de `git ls-tree -r M`; sin coincidencia única → fuera), o exigir `relative_files` en el trabajo que graba la matriz.

**7. Nada dice cómo se obtiene el rootdir de pytest.**
Frases: «`conftest P` (P is a `conftest.py` in the test's directory or any directory above it, up to pytest's rootdir)», edge case «pytest's rootdir is `backend/`».
Problema: el rootdir depende de la invocación de pytest (argumentos, ini-files presentes) que la herramienta no conoce y que no está en la lista de inputs. Con rootdir mal calculado, la regla conftest y el mapeo node-id→ruta de `own file` seleccionan de más o de menos: un `conftest.py` por encima del rootdir real no lo carga pytest, pero la regla lo contaría si la herramienta asume la raíz del repo.
Arreglo: declarar el procedimiento (replicar el algoritmo de rootdir sobre el checkout en H, con qué invocación asumida) o aceptarlo como input del paso.

**8. El exit 3 en rechazos rompe la postura de sombra de la rebanada.**
Frases: «its verdict never changes the CI result: the full suite runs every time, and a missed run exits like a caught one» frente a «it appends its record … and exits with 3».
Problema: un rechazo (matriz de cobertura no subida, `no-shared-lines` tras cambiar de core) pone el paso en rojo en cada PR: la herramienta sí cambia el resultado del CI, que es justo lo que la rebanada promete no hacer. La spec no dice que el paso deba desplegarse como no bloqueante, así que el comportamiento por defecto de cualquier CI incumple la promesa.
Arreglo: decidir el contrato y escribirlo (paso declarado no bloqueante con exit 3 como señal para el equipo dueño, o rechazo con exit 0), reflejándolo en los ejemplos [core] que fijan el 3.

**9. La regla del par depende de `mangle_test_address` y de opciones de junitxml que la spec ignora [sin verificar].**
Frase: «that pytest works out from its node id with a private function, `_pytest.junitxml.mangle_test_address`».
Problema: es una función privada (puede cambiar entre versiones) y el `classname` real depende de `--junit-prefix` y de `junit_family`. Si un repo usa cualquiera de las dos, ningún par casa, todo queda «unmeasured», la selección es toda la suite y el informe da 0% de misses y 0% de ahorro **sin ninguna señal** de que el emparejamiento está roto (la cuota de `tests_with_row_not_in_run` lo delataría, pero solo si alguien la mira).
Arreglo: además de replicar el comportamiento en prosa (eso ya lo hace), cubrir el caso degenerado: decidir si un JUnit donde ningún par casa con ningún contexto es input inservible o al menos warning inequívoco, y documentar que `--junit-prefix` no está soportado.

**10. «a line that is not a record» no tiene definición.**
Frase: «If the file holds a line that is not a record, the tool appends nothing, names the file and the line number …» (ídem el informe).
Problema: ¿un JSON válido con `format: 2`? ¿un objeto al que le falta una clave? ¿línea vacía o con `\r\n`? Una implementación estricta aborta (exit 1) donde otra sigue; la validación del output central queda al arbitrio.
Arreglo: definir el esquema exacto de ambas formas de registro y que cualquier desviación —incluido un `format` distinto de 1— cuenta como «no es un registro».

**11. El merge-base puede no existir y ninguna razón lo cubre.**
Frase: «The merge-base is the merge-base of B and H».
Problema: si B e H no comparten historia (fork reescrito, `--allow-unrelated-histories`), `git merge-base` no devuelve commit. Ninguna razón de rechazo cubre ese caso; dos implementaciones lo reparten entre `base`, `checkout` o fallo genérico (exit 1).
Arreglo: mapearlo a una razón existente (p. ej. `unusable-input` con `base`) y añadirlo a la lista.

## Menores

**12.** «in whole milliseconds»: ¿truncamiento o redondeo, y con qué regla de empate? Diferencias de 1 ms en un registro que debe ser byte-exacto. Fijar una regla.

**13.** Cuando varios patrones de floor casan con el mismo path, la razón «`floor X (P)`» no dice cuál X se cita (¿primero del default, primero de la config?). Fijar un orden.

**14.** «never quote what a file holds» aplicado a la config del floor deja el diagnóstico ciego: «has an invalid pattern» sin poder citar el patrón ni el número de línea. La motivación de la regla es el XML no confiado; bastaría restringirla a JUnit/rerun.

**15.** `no-shared-lines` registra igual dos causas de remedio opuesto (grabación con el core equivocado vs. suite que de verdad no comparte líneas); el informe no puede separarlas y ambas excluyen runs de la tasa de misses. Separar al menos el conteo (sin contextos de test vs. contextos sin líneas compartidas).

**16.** Repeticiones de un par dentro del mismo JUnit (pytest-rerunfailures es común): solo se define la fusión failure+error. ¿`tests` y los tiempos suman todas las apariciones? ¿Y `full_ms` con varios `testsuite` (xdist) es Σ de testcase o el atributo del suite? Fijar Σ de testcase en ambos casos.

**17.** Los registros no identifican el repo: si el informe lee ficheros de varios repos, los `pr` colisionan y las tasas por PR se mezclan en silencio. Declarar que el informe presupone un solo repo.

**18.** Cifras degeneradas del informe sin definir: ahorro con Σ full_ms = 0 y bound de Clopper–Pearson con n = 0. Definir la salida.

**19.** Un diff vacío con run rojo es `missed` por definición aunque ningún cambio pudiera seleccionar nada: variante extrema de la open question de base roja. Documentarlo al menos como límite del número.

**20.** El append al fichero de registros no tiene modelo de concurrencia: dos jobs paralelos sobre el mismo fichero pueden dejar líneas partidas y, desde entonces, todo run muere con exit 1. Declarar el modelo de despliegue (un fichero por job con unión al informar — que el informe multi-fichero ya soporta — o append atómico).

## Supuestos sin verificar

- «the `sysmon` core … records each line only for the first test that runs it» y «coverage's default from Python 3.14».
- Que `mangle_test_address` se comporta exactamente como se describe (params intactos desde el primer `[`, `/`→`.`, solo el `.py` final) y es estable entre versiones; el efecto de `--junit-prefix` y `junit_family`.
- Que los node ids son relativos al rootdir (premisa del edge case `backend/`).
- El formato exacto de los contextos de pytest-cov: `<node id>|setup|run|teardown`, incluida la existencia de la fase teardown.
- «pytest-cov 7 no longer measures subprocesses».
- Que la API pública de coverage expone líneas por contexto (`contexts_by_lineno` o equivalente documentado).
- Que el atributo `time` de `testcase` está siempre presente.
- Que `git diff --name-only` emite rutas relativas a la raíz aunque el cwd sea un subdirectorio (`diff.relative=false`).

## Alcance: lo que sobra o se puede diferir

- **El fichero de rerun** es el bloque más recortable: input extra, emparejamiento, semántica de «not reproduced» y ajuste del veredicto. Si se corta, flaky y order-dependent cuentan como fallos reales y sesgan la tasa; si se corta, etiquetar las cifras. Es defendible mantenerlo, pero es lo primero que sacrificaría si la rebanada no cierra.
- **Conflictos multi-fichero e independencia de orden del informe** solo se justifican si el modelo es «un fichero por job». Si se fija «un solo fichero por repo», se difieren — pero eso choca con el CI paralelo y con el defecto 20: decidir primero el modelo de despliegue.
- **El guard de `no-shared-lines`** protege contra una mala configuración del trabajo propio que graba la matriz. Lo indispensable es rechazar cobertura sin contextos de test; la heurística de «ninguna línea en más de un test» (con su falso positivo en suites sin código compartido) puede esperar a verificar las premisas sobre sysmon.
- Las cifras secundarias del informe (cuotas de unmeasured y de `tests_with_row`, conteos de not-reproduced) son baratas una vez existen los registros y alimentan §13.2; no las cortaría.

## Comprobado sin defecto

Los números de los ejemplos cuadran (Clopper–Pearson 1/3 → 86,5% y 0/30 → 9,5%; ahorros 37,5%, 25%, 12,5%; el registro [core] del run missed es consistente con el fixture y el orden de claves; las reglas de patrones `**` son internamente consistentes con sus ejemplos, incluidos `requirements/base.txt` y `src/shop/config/loader.py`); la semántica de ya-registrado/evaluado/rechazado no se contradice entre la norma y los ejemplos [core]; la serialización JSON descrita coincide con `json.dumps` por defecto (`ensure_ascii`, escapes cortos, hexadecimal minúscula).
