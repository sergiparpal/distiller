# Decisions

## D-001 Option A for Slice 1, with messages and selection rules in modules of their own, 2026-10-10
- Context: There is no template repository for a Python command-line tool yet, so Phase 2 compared three architectures (`notes/2026-10-10-architecture-options.md`) and had another model critique them (`notes/2026-10-10-architecture-critique.md`). The three implement the same behaviour and have the same core modules; they differ in how the modules are cut and in how the [core] examples are tested.
- Chosen: option A, the simplest, with three changes that answer defects the critique found in it. (1) `messages.py` holds the `Rejected` exception and every text the tool writes to stderr, built only from fixed text, values given on the command line, commit ids, the run's key and line numbers (argparse writes the usage errors itself, from the command line alone): the libraries' errors carry text read from the files (defusedxml's, an entity's name and system id; coverage's, what it read from the data file), and in A four modules wrote messages. (2) `selection.py` holds the pure rules, `pair_of`, `match_tests`, `select` and `judge`, so that `evaluate.py` keeps only the command's flow: the record file, the key, the problem order, the record and the exit code. (3) `junit.py` reads both JUnit files, and `cli.py` only parses the arguments, starts a command and catches unexpected failures.
- Rejected: B, load then compute (fifteen modules, a wide `RunInputs`, and a shell/pure boundary that makes `coverage_io` import from `matrix`; of its gains, one home for the messages comes with `messages.py`, and pure tests of the K1 and K2 lines are modest, since K1 still needs an end-to-end test). C, ports and adapters (a fake workspace has to mimic exactly the behaviours most likely to be wrong, such as coverage erasing its data file, and its gain, fast in-memory tests of the [core] examples, is anticipated: the SPEC limits the tool's time, not its suite's).
- Consequences: Easier: one module per input; `evaluate.run` reads like the SPEC's problem order; "never quote what a file holds" is reviewed in one file; the selection rules are tested with literals. Harder: the [core] examples need a git repository, a coverage file and JUnit files in `tmp_path`; renaming a reason or an input touches every reader; later slices, such as the solver or file tracing, will grow `evaluate.py`, to be revisited then and not before.
- Extended by D-004: `selection` also holds `no_column`, `import_only_paths`, `row_counts` and `durations`.

## D-002 The coverage at M is read through a private copy, 2026-10-10
- Context: coverage 7.16.2's `CoverageData` writes to the file it is given. Queried before `read()`, it erases the data for good. `read()` writes coverage's schema into an empty file, which grew from 0 to 53,248 bytes, and into an SQLite database without coverage's tables. Both were run on Python 3.13. The SPEC forbids writing to the inputs and requires coverage's public API.
- Chosen: copy the coverage file into a temporary directory, call `read()` on the copy before any query, and remove the copy when done. coverage never opens the original.
- Rejected: reading in place with `read()` first (an empty file or a foreign SQLite database still gets coverage's schema written into it); checking SQLite's header first (it lets a foreign SQLite database through); opening the file read-only with `sqlite3` (it bypasses the public API that the SPEC requires).
- Consequences: Easier: no input can change, whatever coverage does, and an empty or foreign file reads as one with no measured file, which the SPEC rejects as `unusable-input`. Harder: every run copies M's coverage file, at a cost in time and disk that was under 1 ms for the pilot's 0.6 MB file (notes/2026-10-12-weight-of-m.md); a killed process can leave the copy behind in the temporary directory.

## D-003 Phases enforced by Claude Code hooks, with Stop inside bwrap, 2026-10-14
- Context: Phase 3 prepares this repository, which is also the template for later command-line tools, for an agent. The method writes the tests from the SPEC before the code, so the tests must not come from src/, and they must not change while the code is written. An instruction cannot hold either: the agent writes through Bash as well as through its file tools, a hook that exits 1 lets the action through, and Claude Code's Bash sandbox covers shell commands only, not hooks, MCP servers, plugins or the file tools.
- Chosen: `.claude/phase`, which only the user writes, says `tests` or `implement <commit>`, the commit of the reviewed tests. Four hooks in `.claude/hooks/`, standard library only, enforce it. After an Edit or Write, ruff formats the file and applies its safe fixes, and what is left goes to Claude. In implement, Edit and Write cannot touch the tests or what decides how the checks run: tests/, scripts/, which make lint runs, and the Makefile; at the root, the configuration files that each tool of the harness can read ahead of pyproject.toml or alongside it (pytest.toml, .pytest.toml, pytest.ini, .pytest.ini, tox.ini, setup.cfg, .coveragerc, .coveragerc.toml, pyrightconfig.json, .importlinter), and those of the secret scan, which make verify runs and which also runs at each commit and in CI (.pre-commit-config.yaml, .gitleaks.toml, .gitleaksignore); in any directory, conftest.py, pyproject.toml, ruff.toml, .ruff.toml, .gitattributes and .gitignore, which pytest, ruff and git also read below the root. More is frozen than needed, on purpose: one file too few loosens the net, and one too many costs nothing. In tests, Read, Grep and Glob cannot reach src/, Bash runs only six whole commands, WebFetch and MCP tools are blocked, and every call that goes through is logged; a subagent's calls go through the same hooks. Stop runs `make format lint types` in tests and `make verify`, which is make check without pip-audit, otherwise; in implement it compares the frozen files with the commit through git, and looks for new ones with the root .gitignore's rules alone: that file is frozen, so a change to it shows in git diff, while a nested .gitignore or .git/info/exclude could hide a new frozen file; in every phase it rejects a log that reached inside src/. Everything Stop runs, git included, runs inside bwrap: no network; the home directory, /tmp, /run and /mnt hidden apart from ~/.nvm and the pre-commit cache; only the repository writable, but not its .venv and .git, where a file written would run outside the sandbox later (the format hook's ruff, a .pth file as Python starts, a git hook or setting at the user's next commit); `.claude/settings.local.json` unreadable; and no variable whose name holds TOKEN, KEY or SECRET. /run is hidden because a read-only mount still lets a process connect to a socket, and /run holds the user's session bus, through which systemd starts processes outside the sandbox, as well as the system bus, WSL's sockets and docker.sock. What the agent can fix blocks the stop twice per turn, counted by the prompt's id; the third time, and at once for what it cannot fix, the turn ends with the reason for the user (`continue: false`). `.claude/blocked` excuses red checks and nothing else. The PreToolUse hooks also block when they fail. The agent's own shell runs in Claude Code's Bash sandbox, which reads nothing outside the working directory. In the tests phase, the agent writes outside tests/ only a new module's stubs and its import-linter contract, which the user reviews in the tests commit. `make lint`, and so `make verify` and the Stop of every phase, fails on raw control and invisible characters, which Unicode classes as control, format, line separator and paragraph separator characters, tab and newline apart, in every file git tracks or would add: a Write or Edit call turns a typed escape into the raw character, and that put a U+2028 in docs/SPEC.md and in CLAUDE.md. `scripts/check_characters.py` names the file, the line and the code point, never the character.
- Rejected: a devcontainer, for now. It would put hooks, MCP servers, plugins and the file tools inside the boundary, which the Bash sandbox leaves outside: hooks and MCP servers run with the user's full access, and in bypass mode Edit and Write reach any file outside the repository. It costs Docker and another way to start sessions. A command analyzer for Bash in the tests phase: a file can be read in too many ways, so a list of allowed commands, compared whole, replaced it. A fingerprint of the tree to skip make when nothing changed: Stop takes about 3 s, and claim-ledger's Stop up to 15 s in parallel. Reading the steps of `check` from the Makefile: Stop runs fixed targets. Probing the network before pip-audit: `make verify` leaves pip-audit out, and CI runs make check. A git tag for the tests commit: the agent could move it with `git tag -f`, and `git push --tags` would publish it. Freezing only the pytest and coverage tables of pyproject.toml: whole files are simpler to check. Looking for new frozen files with no ignore rule at all: the caches of pytest, ruff, import-linter and venv carry a .gitignore of their own, which would block every stop in implement. Making only .git/hooks and .git/config read-only in Stop: git diff, git ls-files and make verify pass with the whole of .git read-only. The character check as a target of its own in make verify, or over tracked files only: the tests phase's Stop runs format, lint and types, and the new tests stay untracked until the user's commit.
- Consequences: The user changes phase by hand. To start the tests phase, `rm -f .claude/tests-phase.log && echo tests > .claude/phase`; after reviewing and committing the tests, `echo "implement $(git rev-parse HEAD)" > .claude/phase`; to end a phase, `rm .claude/phase`, and after deciding on a block, `rm .claude/blocked`. In the tests phase, Grep and Glob are out of Claude Code's default tool set on Linux; the documentation says `claude --allowedTools Grep` brings both back and an allow rule in a settings file does not. Edit and Write need a Read first, so the user writes the new signatures of existing modules before the phase, and the agent stops with `.claude/blocked` if one is missing. In implement, pyproject.toml is frozen, its import-linter contracts included. If a new tool writes a cache with a .gitignore of its own, Stop reports that .gitignore as a new frozen file in implement; the fix is to add the cache's folder to the root .gitignore, as with .import_linter_cache/. While one of its commands runs, the Bash sandbox puts a device file at each protected path that does not exist, such as `.bashrc` or `.claude/skills`; inside it, git status listed twenty of them and git add -A failed, so .gitignore lists those twenty, and a real file at one of those paths needs its line removed first. A binary file must be marked binary in .gitattributes, or the character check fails on it. Creating `.claude/blocked` asks for confirmation, as `.claude/` is a protected path. The hooks and the settings are changed by hand, and `make test-hooks` runs the hooks' contract tests. The template needs python3 3.12 or later, make, git, `bubblewrap` and `socat`, Claude Code 2.1.295 or later, `make install`, and, in each user's `~/.claude/settings.json`, what a repository cannot grant under the sandbox's read block. `~/.nvm` holds the node that pyright runs; on a machine with node elsewhere, that directory. Without `strictAllowlist`, bypass mode lets sandboxed commands reach any host.

```json
{"sandbox": {"filesystem": {"allowRead": ["~/.nvm", "~/.cache/pre-commit"]},
             "network": {"strictAllowlist": true, "allowedDomains": ["pypi.org"]}}}
```

## D-004 The record's derived figures as pure functions in selection, 2026-10-17
- Context: An evaluated record holds `no_column`, `import_only`, `tests_with_row`, `tests_with_row_not_in_run`, `selected_ms` and `full_ms`, and the technical sheet's Interfaces gave none of them a function, so they fell to `evaluate` and could be tested only end to end, with a git repository, a coverage file and JUnit files for each case. That made the evaluated-run task too big for one tests-and-implement cycle.
- Chosen: four pure functions in `selection`, which already imports the types they take: `no_column`, `import_only_paths`, `row_counts` and `durations`, in the SPEC's Interfaces. They get a task of their own, after `judge` and before `records`, tested with literals, and the evaluated-run task keeps the end-to-end examples.
- Rejected: leaving them in `evaluate` and splitting the evaluated-run task in two, the evaluated record and then the record file. The second half's tests would likely pass before its implement phase, since appending to a missing file creates it, and tests that pass before their implement phase guide nothing.
- Consequences: Easier: each figure's rules are tested on their own, and the evaluated-run task fits in one cycle. Harder: `selection` has eight public functions instead of four, and one more task comes before `records`; `evaluate` still has to call them in the right place, which only the end-to-end tests check.
